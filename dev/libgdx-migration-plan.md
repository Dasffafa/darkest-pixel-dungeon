# Darkest Pixel Dungeon LibGDX 迁移计划

## 1. 目标与原则

### 1.1 迁移目标

- 保留 Darkest Pixel Dungeon（下称 DPD）现有玩法、数值、存档和视觉行为。
- 将 Android 专用的 Noosa 底层迁移到 LibGDX。
- 首批支持 Android 与 Desktop（LWJGL3）。
- 建立可扩展的 Shader、全屏滤镜、特殊动画和动态字体管线。
- 为后续评估 iOS 等平台保留清晰的平台边界；首期不承诺 Web/iOS 发布。

### 1.2 三类权威来源

| 来源 | 用途 | 不应直接采用的内容 |
|---|---|---|
| 当前 DPD 仓库 | 玩法、内容、存档、资源和现有视觉行为的权威来源 | Android/GLES 专用底层实现 |
| Shattered Pixel Dungeon `v0.7.4a` 至 `v0.7.5e` | 官方早期 LibGDX 迁移路线和旧 Noosa API 映射 | 期间混入的玩法、数值、关卡和资源变化 |
| 用户控制的 `~/Radish_Pixel_Dungeon`（基于 Shattered `v2.4.2`） | 基础迁移完成后，选择性移植 Shader 修复、动态字体等明确增强功能 | 基础 LibGDX 迁移架构，以及未经明确选择的现代 Shattered/Radish 玩法变更 |

### 1.3 实施原则

- 保持 DPD 游戏逻辑为基线，优先替换底层，不以 Shattered `v2.4.2` 重建玩法。
- 基础迁移集中参考 Shattered 第一个 LibGDX 版本及其连续修复提交，按历史顺序移植；在 Android 与 Desktop 基础迁移完成前，不以 Radish 当前架构替代这条路线。
- 保留 Noosa 的上层 API，第一阶段不全面改写为 Scene2D、ECS 或其他对象模型。
- 迁移底层及上游兼容代码允许继续使用 Java；不为语言统一进行 Java 到 Kotlin 的机械转译。
- 新玩法和与上游结构无关的新模块仍优先使用 Kotlin。
- 每个阶段都必须形成可独立审查、可回退的提交，禁止把玩法调整混入迁移提交。
- 移植 GPL 来源代码时保留原许可证、版权与归属说明，并在提交中记录来源版本或提交。
- Agent 负责分析、实现和静态检查；Gradle 构建、运行、真机和视觉验收由用户执行。
- `~/Radish_Pixel_Dungeon` 是只读参考源：可以读取、比较并将有用实现复制到 DPD，但未经单独授权不得修改、清理或提交该仓库。

## 3. 来源标记与变更分类

所有迁移任务和重要提交应归入以下一类：

| 标记 | 含义 | 审查要求 |
|---|---|---|
| `darkest-authoritative` | 保持 DPD 当前行为 | 不得因现代上游行为而改写 |
| `historical-migration` | 参考早期官方迁移 | 记录对应上游提交 |
| `modern-engine` | 采用 Radish 或现代上游底层实现 | 验证与旧 Noosa/DPD 行为兼容，并记录 Radish 来源提交 |
| `intentional-behavior-change` | 有意引入的玩法变化 | 必须独立讨论、实现和验收，不得夹带于迁移 |

建议在迁移记录或提交说明中使用这些标记，不要求写入每个源文件。

## 5. 每阶段工作循环

每个阶段采用相同闭环：

1. Agent 对比 DPD、对应历史提交和 Radish，输出文件/API 映射。
2. 用户确认涉及行为选择的分歧；纯底层映射无需逐项确认。
3. Agent 按小批次实施并进行静态检查，不运行 Gradle。
4. 用户执行 Gradle 构建和运行，将首个完整错误或可复现现象反馈给 Agent。
5. Agent 修复后，用户按本阶段验收表复测。
6. 验收通过后形成单一职责提交，并更新本计划状态。

单批次应尽量限制在一个边界内，例如只处理输入、纹理或音频，避免同时修改多个核心系统。

## 7. 风险与停止条件

| 风险 | 预防措施 | 停止/回退条件 |
|---|---|---|
| 迁移夹带玩法变化 | 来源标记、独立提交、DPD 为权威 | 无法说明行为差异来源时停止合并 |
| 像素对齐和字体产生系统性差异 | 固定截图、逐层校准相机和过滤 | 基础场景尚未一致前不进入效果开发 |
| 旧存档不兼容 | M0 保存样本、保持类名和字段 | 任一关键存档损坏时停止后续结构重构 |
| 多平台抽象泄漏 Android API | 模块边界检查 | `core`/`SPD-classes` 重新依赖 Android 时回退设计 |
| 直接采用现代逻辑破坏 DPD | 现代项目只作底层来源 | 未经批准的玩法差异必须撤出迁移批次 |
| 多 Agent 修改同一核心文件 | 按模块分工、单一接口所有者 | 接口定义发生并行漂移时暂停合并 |
| 一次改动过大无法定位回归 | 小批次、阶段退出条件 | 无法在一个批次内定位首个错误时拆分或回退 |
